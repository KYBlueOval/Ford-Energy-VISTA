# VISTA 2.4.1 — Sponsor Arrival Email Notifications

## Outcome

VISTA now sends the visitor's listed sponsor a branded arrival email after Security completes check-in at the Main Security Front Desk.

The previous check-in option only stored a `Yes` or `No` value. Version 2.4.1 performs the email operation and records the actual outcome.

## Check-in behavior

The **Send sponsor arrival email after check-in** option is selected by default.

After Security confirms check-in, VISTA:

1. Marks the visitor `Checked In`.
2. Assigns the selected visitor badge.
3. Sends the sponsor arrival email.
4. Records the delivery result in the visit, activity history, and audit log.
5. Shows the officer whether the email was sent or requires follow-up.

The sponsor email includes:

- Visitor name and company
- Arrival location
- Check-in date and time
- Visitor badge number and UID
- Confirmation number
- Check-in officer
- A reminder to meet or receive the guest according to escort requirements

Email delivery is intentionally non-blocking. If Google Mail is unavailable, the recipient is missing, or delivery fails, the visitor remains checked in and the failure is recorded for follow-up.

## Spreadsheet additions

Running `setupVista()` adds these `VisitRequests` columns without removing existing records:

- `SponsorNotificationStatus`
- `SponsorNotifiedAt`
- `SponsorNotificationEmail`
- `SponsorNotificationError`

It also adds these Config keys only when they do not already exist:

| Key | Default | Purpose |
| --- | --- | --- |
| `SPONSOR_ARRIVAL_EMAILS` | `YES` | Enables automatic sponsor arrival messages. Set to `NO` for an emergency global pause. |
| `CHECK_IN_LOCATION` | `Main Security Front Desk` | Location displayed in the sponsor email. |

Existing Config values and production URLs are preserved.

## Deployment

1. Replace the Apps Script project's `Code.gs` with `apps-script/Code.gs`.
2. Save the Apps Script project.
3. Run `setupVista()` once and approve any requested permissions.
4. Verify the four new columns appear in `VisitRequests`.
5. Verify the two new keys appear in `Config`.
6. Create a new version of the existing Apps Script web-app deployment.
7. Keep the existing web-app URL and deployment access settings.
8. After GitHub Pages finishes deploying, hard-refresh Security Operations with `Ctrl + F5`.
9. Confirm the footer shows `Version 2.4.1`.

## Proof test

Use a test sponsor email account that you can inspect.

1. Submit or select a visitor request containing a valid sponsor name and sponsor email.
2. Approve the request.
3. Open **Assign Badge and Check In**.
4. Leave **Send sponsor arrival email after check-in** selected.
5. Assign an available badge and confirm check-in.
6. Confirm the completion panel says the sponsor email was sent and names the recipient.
7. Confirm the sponsor receives a branded message with the correct visitor, arrival time, location, badge, and confirmation.
8. In `VisitRequests`, verify:
   - `SponsorNotified` = `Yes`
   - `SponsorNotificationStatus` = `Sent`
   - `SponsorNotifiedAt` contains the send time
   - `SponsorNotificationEmail` contains the sponsor address
   - `SponsorNotificationError` is blank
9. In `VisitActivity`, verify `CHECK_IN` and `SPONSOR_ARRIVAL_EMAIL_SENT`.
10. In `AuditLog`, verify `CHECK_IN` and `SPONSOR_ARRIVAL_EMAIL_SENT` identify the signed-in officer.

## Failure-safety test

Use a test request with the sponsor email blank, then complete check-in with the email option selected.

- Check-in and badge assignment must still succeed.
- `SponsorNotificationStatus` must show `No Sponsor Email`.
- `SponsorNotificationError` must explain that the address is missing.
- Activity and audit history must record the unsuccessful delivery for follow-up.

Finally, check out both test visitors and return their badges.
