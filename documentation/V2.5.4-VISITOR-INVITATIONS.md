# VISTA 2.5.4 — Secure Visitor Invitations & Intake Completion

## Sponsor and Approver account setup

Administration is now the practical identity source for portal accounts.

1. Open **Administration → VISTA Active Directory**.
2. Select **Add User**.
3. Enter the employee name, employee ID/CDSID, email, username, PIN, department, company, and optional badge UID.
4. Select role **Sponsor** or **Approver** and leave the account active.
5. Save the account.

VISTA writes the authentication record to `Users` and synchronizes the matching selectable directory entry to `Sponsors`. Disabling, deleting, or changing the role away from Sponsor/Approver deactivates the corresponding Sponsors entry. Run the existing **Sync VISTA Sponsors** GitHub workflow to publish directory changes immediately; its scheduled run will otherwise publish them automatically.

The account email is the primary visitor-assignment identity and must be the address used in `VisitRequests.SponsorEmail`.

## Invitation workflow

1. A Sponsor, Approver, Admin, or Super Administrator creates a visitor request in the Sponsor Portal.
2. VISTA creates one VisitRequests record with status `Submitted` and `VisitorIntakeStatus` set to `Pending`.
3. The visitor receives an **Action required** email containing a secure intake link.
4. The link opens the standard Visitor Registration page in invitation mode and preloads the sponsor-controlled request fields.
5. The visitor completes personal details, vehicle information, a processed photograph, the safety video, and all seven acknowledgements.
6. Submission updates the existing Visit ID and confirmation number; it does not create a second request.
7. VISTA writes seven `AgreementAcknowledgements` rows, updates the photo and visitor fields, records `VISITOR_INTAKE_COMPLETED`, and emails the assigned Sponsor/Approver.
8. The Sponsor can then approve the completed request. Security can check it in after approval.

Pending requests also display **Send / Resend Intake Email**. This supports requests created before 2.5.4 and replaces a lost or undelivered link. Creating a replacement immediately invalidates every earlier link for that Visit ID.

## Security controls

- The emailed token contains 256 bits of random UUID-derived material.
- Only the SHA-256 token hash is stored in `VisitRequests`.
- The token is cleared after successful completion and cannot be reused.
- The link expires after `VISITOR_INTAKE_INVITATION_DAYS`, but never before the scheduled visit ends plus one day.
- Sponsor, schedule, reason, department, access, escort, and restriction fields are preserved from the sponsor-created record.
- Sponsor-created requests cannot be approved or checked in until `AgreementCompletionStatus` is `Completed`.
- Denied, cancelled, checked-out, expired, invalid, and completed invitations are rejected.

## Deployment

1. Replace the Apps Script project `Code.gs` with `apps-script/Code.gs`.
2. Save the Apps Script project.
3. Run `setupVista()` once. It adds the new VisitRequests columns and the `VISITOR_INTAKE_INVITATION_DAYS` Config key without changing existing Config values.
4. Create a new version of the existing Apps Script web-app deployment and retain the current URL.
5. Allow GitHub Pages to deploy.
6. Hard-refresh Administration, the Sponsor Portal, and Visitor Registration with `Ctrl + F5`.

## Proof-out

1. In Administration, create an active Sponsor test account and confirm matching rows exist in `Users` and `Sponsors`.
2. Run **Sync VISTA Sponsors** and confirm the test sponsor appears in the public registration sponsor picker.
3. Sign into the Sponsor Portal and create a visitor request using an email account you can access.
4. Confirm the visitor email contains **Complete Required Visitor Intake**.
5. Open the link and confirm sponsor, dates, reason, and requested access are preloaded and locked.
6. Complete the missing personal fields, vehicle information, photograph processing, safety video, all seven acknowledgements, typed name, and submission.
7. Confirm the original `VisitRequests` row now contains the photo fields, completed agreement fields, `VisitorIntakeStatus = Completed`, and `VisitorIntakeCompletedAt`.
8. Confirm exactly seven `AgreementAcknowledgements` rows reference the original Visit ID.
9. Confirm `VISITOR_INTAKE_COMPLETED` appears in both `VisitActivity` and `AuditLog`.
10. Confirm the Sponsor receives the completion email and can approve the request.
11. Confirm Security can check in the request only after intake completion and approval.
12. Reopen the invitation link and confirm it is rejected as already completed.
13. For an incomplete test request, select **Send / Resend Intake Email** and confirm the new link works while the earlier link is rejected.

## Config

| Key | Default | Purpose |
| --- | --- | --- |
| `PUBLIC_REGISTRATION_URL` | VISTA public registration URL | Base URL used in visitor invitation emails |
| `VISITOR_INTAKE_INVITATION_DAYS` | `14` | Minimum lifetime of a visitor intake invitation |
| `TRAINING_VIDEO_URL` | Existing value | Safety/site-awareness video displayed during intake |
| `AGREEMENT_VERSION` | Existing value | Version written to acknowledgement records |
| `PHOTO_FOLDER_ID` | Existing value | Google Drive folder for completed visitor photos |
