# VISTA 2.5.2 — Sponsor Approval Governance

## Combined release

This deployment contains both milestones:

- **2.5.1:** sponsor delegation and out-of-office coverage.
- **2.5.2:** sponsor-review reminders, escalation, and Administration oversight.

## New worksheets

Running `setupVista()` adds these worksheets without deleting or rewriting existing records:

- `SponsorDelegations`
- `SponsorReviewReminders`

## New Config values

| Key | Default | Purpose |
|---|---:|---|
| `SPONSOR_REMINDERS_ENABLED` | `YES` | Enables processing when the cycle is run. |
| `SPONSOR_REMINDER_HOURS` | `24` | Age at which an undecided request becomes reminder-due. |
| `SPONSOR_ESCALATION_HOURS` | `48` | Age at which the reminder is treated as an escalation. |
| `SPONSOR_REMINDER_COOLDOWN_HOURS` | `20` | Prevents repeated delivery inside this interval. |
| `SPONSOR_ESCALATION_EMAILS` | blank | Optional comma- or semicolon-separated escalation distribution. |
| `SPONSOR_DELEGATION_MAX_DAYS` | `90` | Maximum duration of one coverage assignment. |

Existing Config values are preserved. Configure `SPONSOR_ESCALATION_EMAILS` before testing escalated distribution.

## Reminder behavior

- Only `Submitted`, `Pending Review`, and `Pending Sponsor Review` visits are processed.
- Reminder recipients include the request sponsor and active delegated approvers.
- Escalations also include valid addresses configured in `SPONSOR_ESCALATION_EMAILS`.
- A script lock prevents concurrent cycles from duplicating deliveries.
- Cooldown is evaluated per Visit ID using the most recent `SponsorReviewReminders` record.
- Delivery success or failure is written to `SponsorReviewReminders`, `VisitActivity`, and `AuditLog`.
- Delivery failure does not change or approve the visitor request.

## Deployment

1. Replace the Apps Script project `Code.gs` with `apps-script/Code.gs`.
2. Save the project and run `setupVista()` once.
3. Review all six sponsor Config values listed above.
4. Create a new version of the existing Apps Script web-app deployment and retain its URL.
5. For automatic processing, run `installSponsorReviewReminderTrigger()` once and authorize the trigger.
6. To keep reminder processing manual, do not install the trigger; Administrators can select **Run Reminder Cycle** from Sponsor Approval Governance.
7. Allow GitHub Pages to deploy, then hard-refresh Administration and the Sponsor Portal.

`removeSponsorReviewReminderTrigger()` removes only triggers whose handler is `processSponsorReviewReminders`.

## Administration proof-out

1. Open **Sponsor Approval Governance** from the Administration launcher.
2. Confirm pending, reminder-due, escalated, and active-coverage totals.
3. Confirm requests younger than the reminder threshold show `Within Target`.
4. Select **Send Reminder** for an eligible request and verify the sponsor receives the branded email.
5. Verify one `SponsorReviewReminders` row plus `SPONSOR_REVIEW_REMINDER` in `VisitActivity` and `AuditLog`.
6. Set a test request older than the escalation threshold, configure a test escalation address, and send the escalation.
7. Confirm sponsor, active delegate, and escalation distribution delivery and `SPONSOR_REVIEW_ESCALATED` records.
8. Immediately run the full reminder cycle and confirm cooldown prevents a duplicate delivery.
9. Create and cancel a delegated coverage assignment from Administration.

## Sponsor proof-out

Follow `V2.5.1-SPONSOR-DELEGATION.md`, then confirm delegated requests show `Covering for` attribution and disappear as soon as coverage is cancelled or expires.

## Production safeguards

- Begin with test recipient addresses in `SPONSOR_ESCALATION_EMAILS`.
- Test the manual cycle before installing the hourly trigger.
- Keep the reminder and escalation thresholds far enough apart for normal sponsor response.
- Monitor Apps Script email quota and the first production `SponsorReviewReminders` records.
